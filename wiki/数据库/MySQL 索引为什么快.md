# 1. MySQL 索引为什么快

> 2026-07-30 学习会话（10 分钟，kg-learn）产出。
> 主题：InnoDB 索引加速查询的原理。**核心是纠正一个旧笔记里的错误理解。**
> 关联：`archive/05 数据库/01 MySql.md` 第 24 章（索引操作与实验数据）

---

## 1.1 起点：旧笔记里的一句错话

`archive/05 数据库/01 MySql.md` 第 24.1 节原文写：

> 其实索引的本质就是将表改为二叉树，这样检索的速度会变得非常快

**这句话是错的**（当年抄教程时就错了，不是后来 MySQL 变了）。
InnoDB 用的是 **B+ 树**，不是二叉树。而"为什么偏偏不能用二叉树"这个问题，
答案几乎就是索引加速原理的全部——所以这个错误反而是最好的切入点。

旧笔记里**对的部分**（实验数据，仍有效，800 万行 emp 表）：

```sql
select * from emp where empno=200000;    -- 有索引  0.006s
select * from emp where ename="xlLZNP";  -- 无索引  6.431s
```

`emp.ibd` 约 500MB。这两个数字是后面所有推导的锚点。

---

## 1.2 我原本的理解 vs 实际（误解清单）

这一节是本页最值钱的部分——记的是我个人的认知坑，不是通用知识。

### 误解 1：慢是因为"循环 800 万行做比较"

**我原以为**：不走索引 = MySQL 在数据库里一行一行循环，逐行比条件，
行多所以慢；如果还有联表查询就更慢。

**实际**：全表扫描确实要逐行比，但**比较本身几乎不花钱**。
CPU 比 800 万次是几十毫秒的量级，测出来是 6.4 秒，差了两个数量级，
说明成本根本不在 CPU。

**真正的成本单位是「页」**：InnoDB 磁盘与内存之间搬数据的最小单位是
**数据页（page），默认 16KB**。想读某一行，必须把包含它的整个 16KB 页搬进内存。

```
500MB / 16KB ≈ 32000 个页
```

**6.4 秒 = 从磁盘搬 32000 个页的代价。**

所以索引的目标不是"少比几次"，而是：**能不能只搬 1~3 个页就拿到那一行。**

> 这个转换是今天最大的啊哈时刻：把"成本 = 行数"换成"成本 = 页 IO 次数"，
> 后面所有结论（包括为什么小表加索引没用）都能自己推出来。

### 误解 2：以为查询"类似二分，条件不断减半"

**我原以为**：数据查询大致是二分，每次靠条件把范围砍一半。

**实际**：方向对，**但二分的单位是页，不是行**；而且叉数远不止 2。

### 误解 3（最关键）：以为"先在索引里拿到 key，再去表里找那一行"

**我原以为**的模型：

```
索引树 → 找到 key → 再去 32000 个页里找到对应数据行   ← 多了一步，错
```

当时的具体困惑："如果有 32000 个页，我拿到 key=100 之后，
怎么知道它在哪一个页里？"

**实际：这一步不存在。** 那 32000 个页**不是**堆在一边等着被搜索的散装数据，
**它们就是 B+ 树的叶子层**。整张表就是一棵 B+ 树，没有"树 + 表"两份东西。
这叫**聚簇索引（clustered index）**：数据按主键顺序直接组织在树的叶子里。

```
索引树的叶子页，本身就是数据页
→ "找到 key" 和 "找到行" 是同一个动作
```

**这个疑问之所以会产生，恰恰是因为聚簇索引的设计消灭了它。**
如果换成二级索引，这个疑问就重新成立了（见 1.6 回表）——所以这个困惑
其实是提前撞上了聚簇索引 vs 二级索引的分界线。

## 1.3 为什么不能用二叉树

假设真用二叉树存 800 万行：

- 树高 `log₂(8_000_000) ≈ 23` 层
- 每层一个节点，节点散落在磁盘不同位置 → **每下一层就是一次随机磁盘 IO**
- 23 次 IO。比 32000 次好，但远不够

更致命的是**空间浪费**：二叉树节点里只有 `key(8B) + 左指针 + 右指针`，
二十几个字节，但页是 16KB —— 磁盘还是得把整个 16KB 搬进内存。

**搬 16KB，只换来"往左还是往右"这 1 bit 的信息量。**

关键洞察：

> 既然一次 IO 必须搬 16KB（这是硬约束，改不了），
> 那就把这 16KB **塞满 key**，让每次 IO 做出最大幅度的范围收窄。

同样的 16KB，塞 1170 个 key 后换来的是"落在 1171 个区间里的哪一个"，
信息量从 1 bit 变成约 10 bit。**IO 成本不变，收窄能力翻十倍。**

## 1.4 B+ 树：把叉数开到最大

按 bigint 主键（8B）+ 页指针（6B）估算，一个 16KB 页大约放 **1170 个 key**。
所以这棵树不是 2 叉，是 **~1170 叉**。这是 B+ 树高度极矮的唯一原因。

### 三层各存什么

| 层 | 叫法 | 页里存什么 | 一页容量 |
|---|---|---|---|
| 根 | root | key + 子页号，**不存数据** | ~1170 条 |
| 中间 | 内节点 | key + 子页号，**不存数据** | ~1170 条 |
| 叶子 | leaf | key + **整行数据** | ~16 行（行越宽越少） |

非叶子层只放"路标"所以塞得密，叶子层放真货所以塞得少。

### 2000 万行反推树高

```
叶子层：2000万 / 16   ≈ 1_250_000 个叶子页
中间层：125万 / 1170  ≈ 1068 个中间页
根  层：1068 个 key   → 1 个根页装得下 ✓
```

**2000 万行的表，树高只有 3。**

更重要的是：根页 + 1068 个中间页加起来才约 17MB，**全部常驻 Buffer Pool**。
所以真正要碰磁盘的只有最后那个叶子页 —— **1 次 IO**。

```
32000 次页 IO  →  1 次页 IO
6.431s        →  0.006s
```

### 查找路径（每步靠指针直接跳，从不搜索）

以 key=1500 为例：

```
根页（常驻内存）
  key < 1000    → 页号 #47
  1000~2000     → 页号 #83      ← 落这里
  2000~3000     → 页号 #91
      ↓ 直接读 #83（不搜索，指针跳）
中间页 #83
  1400~1500     → 页号 #7712
  1500~1600     → 页号 #7713    ← 落这里
      ↓ 直接读 #7713
叶子页 #7713  ← 这就是数据页
  [1500, 张三, 2000.00, ...]   ← 行在这里
  [1501, 李四, 3000.00, ...]
```

页内最后一步才是真正的比较：16KB 已在内存，靠页内 slot 目录二分几次定位到行。
纯 CPU，纳秒级，不计入成本。

### 为什么是 B+ 树而不是 B 树

叶子页之间有**双向链表**串联。所以 `where empno between 1000 and 2000`
这类范围查询，定位到起点后顺着链表往后读即可，不必回到树上重新走。

B 树的数据分散在所有层级，做不到这种连续扫描 —— 这是选 B+ 而非 B 的关键理由。

## 1.5 一句话心智模型

> **索引快，不是因为少比了几次，而是因为把"扫 32000 个页"变成了"精准搬 1~3 个页"。**
> B+ 树选 1170 叉而不是 2 叉，唯一原因是：既然磁盘一次必须搬 16KB，
> 就要让这 16KB 发挥最大的范围收窄能力。

### 自测题与我的回答（已验证掌握）

**问**：有人说"我这表只有 500 行，加了索引查询没变快，索引是不是没用？"
用上面的模型解释为什么。

**我的回答**：核心是数据量还没到，索引本质是减少页的查询 IO。

✅ 正确。500 行整张表就一两个页，全表扫描本来就只要 1 次 IO，
索引再快也快不过 1 次，还白搭写入成本和磁盘空间。
**这也解释了旧笔记里那句"针对大量数据得情况下，数据量不大就不用处理"
背后的真正原因。**

## 1.6 下一节的入口（今天未展开）

既然整张表就是主键的那一棵树，那么：

```sql
create index empno_index on emp(empno);
```

这棵**二级索引**树的叶子里放什么？

- **不放整行** —— 整行只存在主键那棵树里，复制一份太浪费空间
- **放主键值** → 于是需要**回表**：先在二级索引树找到主键，再拿主键去主键树走一遍
- **两棵树 = 两次查找**

于此衍生出一整片话题，留待下次：

- 回表的成本，以及**覆盖索引**（叶子里的字段够用就不回表）
- **最左前缀**原则（联合索引为什么讲顺序）
- **索引失效**的常见场景（函数包裹字段、隐式类型转换、`like %xx`）
- 用 `explain` 读执行计划验证以上

> 误解 3 的那个困惑（"拿到 key 怎么找到行"）在二级索引场景下**重新成立**，
> 而答案就是回表。下次从这里接上。
