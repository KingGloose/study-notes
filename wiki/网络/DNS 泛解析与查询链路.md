## 1.1 先建立心智模型:DNS 是一棵分层的树

DNS 的本质是把「人类可读的名字」翻译成「机器用的 IP」。它不是一张集中式大表,而是一棵**分层、分布式、可委派**的树,和域名的分级结构一一对应:

```
                    . (根)
                   /   |   \
                com    cn   org        ← 顶级域 TLD
                /
        zhuanspirit                    ← 权威服务器管这一段
          /    \
        oa     test                    ← 继续往下,谁管辖谁负责
```

每一层只知道「下一层归谁管」,把查询**委派**下去。这套设计让全球域名能分散管理:根不需要知道 `oa.zhuanspirit.com` 是什么,它只要知道 `com` 归谁管;`com` 只要知道 `zhuanspirit.com` 的权威服务器在哪。

---

## 1.2 一次完整查询:从浏览器到 IP

以第一次访问 `oa.zhuanspirit.com`(缓存全空)为例,拆成两个阶段。

### 1.2.1 阶段一:本地能不能直接答

浏览器/操作系统会**先查缓存**,顺序大致是:

1. **浏览器自身 DNS 缓存**(有 TTL)。
2. **操作系统缓存 + `hosts` 文件**。`hosts` 优先级很高,是本地写死的静态映射——这也是前端开发用 `127.0.0.1 xxx.com` 做本地调试、以及代理工具「劫持」域名的基础。
3. **系统配置的 DNS 服务器**(通常是路由器或运营商/公司内网的递归解析器)。

只要任一层命中,直接返回,不再往下走。全空时,请求交给「递归解析器」。

### 1.2.2 阶段二:递归解析器代你满世界问(迭代查询)

递归解析器(recursive resolver)是「跑腿的」,它替你完成一连串迭代查询:

```
resolver → 根服务器:   oa.zhuanspirit.com 的 IP?
根       → resolver:   我不知道,但 com 归这些 TLD 服务器管,去问它们
resolver → TLD(com):  oa.zhuanspirit.com 的 IP?
com      → resolver:   我不知道,但 zhuanspirit.com 的权威服务器在这,去问它
resolver → 权威服务器:  oa.zhuanspirit.com 的 IP?
权威     → resolver:   是 1.2.3.4
resolver → 你:         1.2.3.4(并按 TTL 缓存起来)
```

两个术语别混:

- **递归查询**:你对 resolver 说「你负责给我最终答案」。你和 resolver 之间是递归。
- **迭代查询**:resolver 对根/TLD/权威一级级问,每次拿到的是「去问下一个谁」的线索。resolver 和上游之间是迭代。

**权威服务器(authoritative)**是链路终点——它持有 `zhuanspirit.com` 这个区域(zone)的真实记录,答案以它为准。你配泛解析记录,就是配在这台权威服务器上。

## 1.3 常见记录类型(够用版)

| 类型 | 作用 | 例子 |
| --- | --- | --- |
| A | 域名 → IPv4 | `oa.zhuanspirit.com A 1.2.3.4` |
| AAAA | 域名 → IPv6 | `oa... AAAA 2001:db8::1` |
| CNAME | 域名 → 另一个域名(别名) | `www CNAME oa.zhuanspirit.com` |
| NS | 指明某子域归哪台权威服务器管(委派) | `test NS ns1.xxx.com` |
| MX | 邮件服务器 | 收邮件用 |
| TXT | 任意文本(常用于域名归属验证) | Let's Encrypt DNS-01 会用,见下一篇 |

CNAME 有个约束:一个名字有了 CNAME 就不能再有其他记录(A/MX 等),因为它整个是「别名重定向」。这也是根域(`zhuanspirit.com` 本身)通常不能用 CNAME 的原因。

## 1.4 泛解析记录:`*` 怎么匹配

泛解析就是权威服务器区域文件里的一条 `*` 记录:

```
*.test.zhuanspirit.com.   A   192.168.170.88
```

### 1.4.1 匹配规则

- **只匹配一个层级**(延续上一篇的硬规则)。`*.test.zhuanspirit.com` 匹配 `a.test.zhuanspirit.com`,**不匹配** `a.b.test.zhuanspirit.com`。
- **`*` 只能在最左边**,且只能占一整段(不能写 `oa-*.test...` 这种半通配,标准 DNS 不支持前缀部分通配)。
- 它匹配的是「这一层里**没有被更精确记录覆盖**的所有名字」。

### 1.4.2 精确记录优先(最关键的一条)

**精确匹配永远优先于通配符。** 同时存在时:

```
*.test.zhuanspirit.com.       A   192.168.170.88   ← 兜底
oa.test.zhuanspirit.com.      A   10.0.0.9         ← 精确
```

- 查 `oa.test.zhuanspirit.com` → 命中精确记录 → `10.0.0.9`。
- 查 `foo.test.zhuanspirit.com` → 没精确记录 → 落到泛解析 → `192.168.170.88`。

这个「精确优先、通配兜底」的组合非常实用:泛解析负责「所有人默认落到测试机」,个别需要特殊指向的名字再单独配一条精确记录覆盖掉即可。

### 1.4.3 泛解析的几个坑

1. **`*` 不匹配自身的父名**。`*.test.zhuanspirit.com` 不会匹配 `test.zhuanspirit.com`(裸名),裸名要单独配。
2. **一旦某个名字有了任意精确记录,通配符对它整个失效**——包括记录类型不一样的情况。比如给 `oa.test...` 配了个 MX,那么查它的 A 记录时也**不会**再回退到 `*` 的 A 记录,而是直接返回「无此类型记录」。这是 RFC 里一个反直觉的点。
3. **收敛过宽**。泛解析会让**任何**拼写(包括打错的、别人乱试的)都解析成功,可能掩盖配置错误,也可能带来安全面(任意子域都指向你的机器)。

## 1.5 TTL 与缓存:为什么改了 DNS 不立刻生效

每条记录都带 **TTL(Time To Live,秒)**,告诉各级缓存「这条答案能缓存多久」。

- TTL 内,resolver 直接用缓存答复,不再回源问权威服务器 → 快,但你改了记录不会马上生效。
- 所以计划改解析(尤其切 IP)前,通常先把 TTL 调小(如 300s),等旧 TTL 过期后再改,减少「新旧 IP 并存」的窗口。

排查 DNS 时,`dig` 比 `ping` 更有用:

```bash
dig oa.zhuanspirit.com          # 看最终 A 记录和 TTL
dig +trace oa.zhuanspirit.com   # 从根开始完整跑一遍迭代过程,定位哪一级出问题
dig foo.test.zhuanspirit.com    # 验证泛解析是否对任意前缀都能返回
```

## 1.6 串回泛域名场景

把本篇套回系列主线:

- 运维在 `zhuanspirit.com` 的**权威服务器**上加一条 `*.test.zhuanspirit.com` 的泛解析,指向测试环境入口机。
- 于是 `oa-zhangjiahui04.test.zhuanspirit.com`、`oa-任意人.test.zhuanspirit.com` 全都能解析到同一台入口机,**不用逐个加记录**。
- 到了入口机之后,再由 [[nginx 泛域名转发]] 按具体子域名区分是谁、转发到哪。
- 而要让这些名字能跑 HTTPS,需要一张覆盖 `*.test.zhuanspirit.com` 的通配符证书——正是下一篇 [[通配符 HTTPS 证书]] 的内容。
