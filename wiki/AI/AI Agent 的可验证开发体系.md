# 1. AI Agent 的可验证开发体系(把手动验证变成回归测试闭环)

> **来源**:B站视频《我做 AI Agent 一年,90% 在做表面功夫——直到我换了思路》,UP主「数字黑魔法」(芯片设计验证从业者),BV1o87764Ebs,14:27。
> 逐字稿见 [[../../raw/bili-BV1o87764Ebs-AI-Agent开发的可验证体系.md]](B站 AI 字幕,有识别误差)。
> **为什么值得留页**:它不是"怎么写 Agent"的通用教程,而是一条**从瓶颈出发的工程决策链**——发现 90% 时间在手动验证 → 找到理论依据 → 借另一个成熟行业(芯片验证)的方法论 → 落成具体架构。这套推理路径是 AI 直接问答给不出的东西。
> 标注约定:[视频观点] / [信源] / [AI 补充]。

---

## 1.1 一句话主旨

做 AI Agent 时真正吃掉时间的不是写代码,是**反复手动验证一个不确定的系统**。
解法不是更努力地测,而是**先把系统改造成"可被另一个 AI 验证"的形态**,再把验证做成自动回归闭环——于是人的价值从"写实现"上移到"定义什么算对"。

---

## 1.2 起点:被逼到墙角的 90%

作者自己统计的时间分配 [视频观点]:

- 写代码 + 做设计:**10%**
- 手动测试:**90%**——开网页、灌数据集、盯着 Agent 一步步跑、用人脑判断这次比上次好还是坏

痛点的三层递进(这是关键,不只是"慢"):

1. **慢**:每次验证要人守在屏幕前点。
2. **脆**:系统本身不确定,改一句 prompt 可能整体崩。
3. **盲**:很多时候连"到底有没有坏"都看不出来,只能反复跑,靠感觉。

第 3 层才是真问题。工作已经从"写代码"退化成"反复验证一个自己都快看不懂的系统"。

---

## 1.3 理论依据:验证的不对称性

- **Asymmetry of verification(验证的不对称性)**:有些任务做出来很难,但验证做得对不对很容易(数独是典型)。 [信源]
- 由此推出 **Verifier's Law**:*任何可解且易于验证的任务,终将被 AI 解决*。 [信源]
- 提出者 Jason Wei(OpenAI o1 / Deep Research 共同作者,2025 年从 OpenAI 转 Meta)。 [信源]

> **核对备注** [AI 补充]:Jason Wei 本人博客用的词是 **verifier's rule**(《Asymmetry of verification and verifier's rule》,jasonwei.net),社区和二次传播里普遍写成 **Verifier's Law**,视频用的是后者。指同一件事,查原文时两个词都要试。

**它和那 90% 的关系**(视频的推理落点,也是整页的枢纽) [视频观点]:

之所以 90% 时间花在验证上,恰恰因为对自建 Agent 来说 **生成很便宜、验证很贵**——不对称是反着的。
所以要做的事情不是优化验证效率,而是**亲手把"难验证"改造成"易验证"**。一旦易验证成立,按 Verifier's Law,剩下的收敛过程就该交给 AI。人的角色随之变成:**制造这个可验证的环境**。

---

## 1.4 类比:芯片验证行业 30 年前就走过这条路

作者的本职是芯片设计与验证,这是本页最有信息量的部分——**一个已经被现实倒逼过的行业,给软件 Agent 开发提供现成方法论**。 [视频观点]

- 冷知识:**写芯片代码的人往往比验证的人少**,流片前投在验证上的人力常是设计的 2~3 倍或更多。
- 原因是错误成本不可逆:流片出错就是几百万美金打水漂,没有"改个 bug 重新部署"这种好事。
- 于是行业核心能力不是"会写 Verilog",而是**会设计验证体系**:怎么设计回归测试主动暴露 bug、在哪埋检查点、怎么衡量测得够不够全。

**形状同构** [视频观点]:当年 EDA 工具让"写 Verilog"变便宜,价值就转移到验证体系;今天 AI 让"写代码"变便宜,价值同样转移到"能不能让每次改动都被验证"。

---

## 1.5 落地第一步:先改造系统,而不是先写测试

反直觉的一点:第一件事不是写测试,而是**把自己的 Agent 改造成对别的 Agent 友好的系统**。 [视频观点]

原因:原系统入口是网页 UI,从第一天就是为人的眼和手设计的。测它就必然要有个人在那点。测试写不出来不是测试的问题,是接口的问题。

### 1.5.1 「面向 AI Agent 开发」的三个判据

拿来自查任何系统是否真的 AI 友好 [视频观点]:

1. 脱离人的眼睛和 UI 之后,**它还跑得起来吗**?
2. 运行过程中的**中间状态有没有留下足够信息**,让另一个 Agent 看得懂?
3. 有没有**专门设计接口**,让 AI 自主拿到这些信息?

具体到他的场景:要让 codex 看到整条 workflow 长什么样、中间调了哪些工具、每步拿回什么数据。**如果这些信息一离开 UI 就消失、或 workflow 离开 UI 就停,说明接口仍然是为人设计的。**

### 1.5.2 两条改造路线与选择

| 路线 | 做法 | 视频的取舍 |
|------|------|-----------|
| A. MCP 驱动 UI | 让 AI 通过 MCP 模拟人操作网页,靠多模态观察 | 能跑通,但 authorization、corner case、效率上都不如 B 直接 |
| B. 前后端彻底分离 | 后端成为可独立运行的 Agent,全部调用走命令行;前端退化为展示与人工操作 | **选这条** |

工程代价(踩坑,值得记) [视频观点]:他们原先重度使用 Vercel AI SDK,开箱好用,但**要做到前后端分离、后端脱离前端长时间稳定自跑,需要额外花不少功夫**。

### 1.5.3 学术侧的同一结论

- 普林斯顿 SWE-agent 提出 **ACI(Agent-Computer Interface)**:LM Agent 是**一类全新的用户**,和人不同,需要专门为它设计接口。 [信源:SWE-agent, Princeton Language and Intelligence, 2024-05, arXiv:2405.15793]
- 视频转述其实验结论:**接口设计好不好对 Agent 表现的影响,甚至大过换一个更强的模型**。 [视频观点]
  - [AI 补充] 论文核心主张确实是"ACI 设计显著影响 Agent 表现",方向一致;"影响大过换模型"这个强弱比较属于转述措辞,要引用请回原文核对具体实验。

> 一句话收口:所谓"面向 AI Agent 的编程/服务",核心从来不是某个具体技术,而是**你做的东西能不能被另一个 Agent 快速、主动地拿到它需要的信息**。 [视频观点]

## 1.6 落地第二步:为不确定系统构建回归测试

概念就是 regression test,难点在于**被测对象不确定**。

### 1.6.1 Happy path 作为验收标准

加新工具时,心里本就有明确预期:什么条件下该触发、触发后工作流该怎么走。这条期望路径叫 **happy path**,它就是新功能的验收标准。 [视频观点]

### 1.6.2 谁来当裁判:两层裁判架构

Agent 输出是一大段自然语言 + 一条运行路径,不是能相减的数字,传统"过 / 不过"二分类不够用。解法是**把裁判拆两层**: [视频观点]

**第一层 · 确定性断言(Assertion)**
硬性检查,例如:工具是否触发?跑到某一步中间状态有多少条记录?覆盖到哪些情况?
特点:**绝对可靠、确定、零成本**。

**第二层 · LLM 裁判(supervisor)**
只处理第一层卡不住的模糊部分。两个关键细节:

- **上下文必须干净**:它不参与开发,不知道代码来龙去脉,眼里只有"对的预期"。(避免被实现细节带偏而给出宽容判定)
- **不判对错,做量化打分**:面对没有标准答案的输出,用分数衡量"好了多少 / 差了多少",而不是二分。

### 1.6.3 直接搬自芯片验证的三个概念

`assertion`(断言) / `coverage`(覆盖率) / `scoreboard`(比对记分板)。 [视频观点]
差别只在于:Agent 本身有模糊地带,**对不确定性的容忍度要比硬件验证高一些**。

### 1.6.4 攒案例:两类来源

- **固化 happy path**:每开发一个功能,就把它的期望路径沉淀成一条回归用例。
- **从真实用户和线上测试里捞**:那些自己根本没设计过的五花八门输入。

前者保证"不退步",后者保证"尽量没盲区"。 [视频观点]

### 1.6.5 每个新功能配一个 flag(作者自评最关键的细节)

有开关就有"开 / 关"两个版本,跑同一套回归测试即可**清楚看到新功能到底带来了什么:哪些变好、哪些被悄悄弄坏**。 [视频观点]

> [AI 补充] 这本质是把 A/B 对照引入开发内环。对确定性系统它只是便利,对 Agent 这种"改一句 prompt 全局漂移"的系统,它是**唯一能把变化归因到某次改动**的手段——否则你只知道结果不一样,不知道是谁造成的。

## 1.7 闭环:人退出内环

把上面拼起来,交给 coding agent(codex)执行的开发循环变成 [视频观点]:

```
新需求
  → 先设计回归测试(定义什么算对)
  → 设计 feature flag
  → 写实现
  → flag 关 / 开 各跑一遍回归测试
  → 用测试结果做反馈,改代码
  → 直到通过
```

这个循环里**人不参与**。人只做一件事:**把"什么算对"定义清楚**,剩下的由闭环自己收敛。
呼应 1.3 的理论:**能验证一个解,就等价于为 AI 造好了一个环境。**

---

## 1.8 作者自己的免责声明(比方案本身重要)

视频结尾明确说:前后端分离、回归测试这些做法技术博文里到处都有,反复讲它们**不是让你照抄**,而是想让人看见**为什么会做出这样的技术决定**——"如果不是那 90% 的浪费把我逼到墙角,我可能不会做这个决定"。 [视频观点]

真正要迁移的问题是:**你自己的工程里,有没有类似的瓶颈正在悄悄吃掉时间?**

以及一句反向提醒 [视频观点]:一年前争的是"要不要用 AI 写代码",现在没人争了,该问的是"怎么用才比别人更快"。**原本 10 分钟的事用 AI 干了 2 小时、结果一样,那是本末倒置。**

- [[Graph Engineering 与多智能体编排]]:**独立收敛到同一结论的另一篇**。那篇作者来自 Agent 平台工程,提出 Verifier(职责是推翻而非重写、必须干净上下文)+ 让代码兜底确定性——和本页的两层裁判(assertion + 干净上下文的 LLM 打分)是同一个设计,而两边的经验来源完全不同(芯片验证 vs Agent 平台)。那篇还补了一层本页没讲的:**古德哈特定律/目标失明**——连裁判标准本身也可能是错的(客服"工单解决率"涨了 5 个月而客户流失翻倍)。

- [[KimiCode Agent 架构演进]]:本篇讲「怎么让 Agent 产出可被验证」,那篇讲「Agent 自身该怎么架构」。
  那篇 `agent-core/tools/` 的工具边界与 `loop/retry.ts` 的重试机制,正是本篇可验证体系所依赖的基础设施形态。

- [[../NodeJS/子进程 spawn 管理]]:**本页 1.5.2 "所有调用做成命令行控制"那一步的实现细节**。命令行执行能力做不稳(超时杀不干净、输出丢尾巴、孙进程逸逸),上面这套回归测试闭环的结果就不可信。
- [[AI Native 时代的研发组织]]:高度互补,而且是**同一命题的两个尺度**。
  - 那篇讲**组织层**:新瓶颈是"系统的信息形态不是为 AI 设计的",提出 Harness 层要把一切做成 AI 友好形态。
  - 本篇是**工程层的实例**:1.5 的三个判据(离开 UI 还跑不跑得起来 / 中间状态是否可读 / 有没有给 AI 的接口)就是"信息形态 AI 友好"的可执行清单;两层裁判 + 回归测试 + flag 就是 Harness 的具体一块。
  - 两边都指向同一个角色转移:人从做实现 → 造环境 / 定标准。
- **MCP**(index 08):本页给出一个**不选 MCP 的场景**——用 MCP 模拟人操作 UI 可行,但 authorization、corner case、效率都不如前后端分离。MCP 是让 AI 接入既有工具的通用协议,不是"给 AI 造原生入口"的替代品。
- **Skills / 渐进式披露**(index 08):同一思路的另一种表达——都是在为 AI 这个"新用户"设计专门接口,而不是让它去适配人的界面。
- **本库的摄入体系**(`skills/`,分层摄入原则):`AGENTS.md` 里"多模态 → 文字 → 沉淀""本地转一次永久复利"和本页 1.5 是同一判据的不同应用面——**信息必须落成能被 AI 主动、低成本拿到的形态**;区别是本库解决"知识可检索",本页解决"运行状态可验证"。
