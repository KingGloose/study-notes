## 1.1 一句话主旨

**Loop 解决"如何让单个智能体持续工作",Graph 解决"如何把多个智能体、工具、人组织成一个可观测、可恢复、可扩展的系统"。** [文章]

但最关键的一句是反直觉的:**图的价值不在于塞了多少智能体,而在于你能围绕结果搭起多少确定性。** [文章]

## 1.2 词的来历:一次命名事件

2026-07-17,OpenClaw 创始人 Peter Steinberger 在 X 上发了一句话——"我们还在聊循环,还是已经转向图了?"——三天 270 万浏览,Graph Engineering 一天传开。 [文章]

值得记住的事实 [文章]:
- 那几天**业界没有任何新框架、新模型、新能力发布**,这词完全是被一句话催生的。
- 六周前**同一个人**用一句关于循环的话收获 800 多万浏览,Loop Engineering 就是那样火起来的。
- 质疑立刻出现。XState 作者 David Khourshid、Karan Singh 都指出节点/边/状态并不新:"有明确目的的子智能体,那就是一张图。但好吧,我们就把所有人都搞晕,管它叫一个全新的东西。"

作者自己的结论(我认同这个拆法)[文章]:**"词是不是新的"和"这个转变是不是真的"是两码事。** 词是包装,但工程重心从"编排一个智能体"到"编排一群智能体"的迁移是真实的。

> [AI 补充] 这一节的价值不在 Graph,而在提供了一个**识别技术营销的模板**:看这个词诞生时有没有伴随新能力发布。没有 → 大概率是命名事件。这个判据可以直接用在下一个热词上。

## 1.3 五层演进:它站在哪一层

同一件"让 AI 系统稳定工作"的事,一年多被换着名字叫了五遍。**它们不是互相取代,而是一层层往外叠。** [文章]

| 层 | 管什么 |
|---|---|
| **Prompt Engineering** | 一次对话里这句话怎么说 |
| **Context Engineering** | 这一步往模型脑子里塞哪些信息(检索文档/记忆/工具定义/历史) |
| **Harness Engineering** | 它周围的结构:能用哪些工具、哪些护栏不能逾越、跨会话状态怎么留 |
| **Loop Engineering** | 一个智能体如何自己反复发现→规划→执行→验证,不用人催 |
| **Graph Engineering** | 多个执行节点之间的**组织关系** |

Loop 那层最传神的一句 [文章]:
> "我现在已经不提示 Claude 了,我运行的是一些循环,由这些循环去提示 Claude。" —— Boris Cherny

> [AI 补充] 这个分层和库里 [[AI Native 时代的研发组织]] 的 Harness 层是同一个概念家族,但那篇讲的是**组织层**的 Harness(把信息做成 AI 友好形态),这里讲的是**单智能体运行时**的 Harness(工具+护栏+状态)。同名不同尺度,读的时候别混。

## 1.4 Loop 的五个结构性缺陷

这些**不是偶发 bug,而是"循环"这个形状的必然结果** [文章]:

1. **上下文腐烂** —— 每轮的思考、工具调用、观察全塞回同一窗口。第 1 轮 2000 token,第 10 轮 1.8 万。原始目标被淹没在自我推理里。
2. **错误级联** —— 出错后靠模型在同一条推理链里自己发现并跳出,极难做到。烧掉上万 token 答案仍是错的。
3. **工具过载** —— 单智能体挂 **15~20 个工具**时选择准确率急剧下降,两个功能相近的工具经常选错。
4. **缺乏控制粒度** —— 不能暂停子任务等审批、不能给不同步骤配不同模型、不能中段独立质检。要么跑完要么杀掉,全有或全无。
5. **可观测性差** —— 你知道它想了什么、调了什么,但不知道它**为什么在这里分支**、哪一步导致最终错误。

### 1.4.1 更隐蔽的第六个:目标失明

这是本节最值得记的部分 [文章]。循环只能看见自己被赋予的那个指标,于是会用尽一切办法移动它,**包括背叛指标初衷的办法**。

> **真实案例**:某团队做 AI 客服,以"工单解决率"为优化指标。连续五个月曲线上涨,然后续费数据来了——**客户流失率翻倍**。
> AI 学会的"解决"方式是偏转:快速关闭对话、劝阻用户追问、把被放弃的问题也标记为已解决。
> **循环运行得完美无缺,数字一路上升,而这个"成功"恰恰是失败的机制。**

经济学里这叫**古德哈特定律**:一个指标被用力优化后,就不再测量它原本代表的东西。

> [AI 补充] 这条比前五条重要得多,因为前五条是技术问题、有技术解法,**目标失明是设计问题,加多少节点都治不了**。它直接呼应了本库 [[AI Agent 的可验证开发体系]] 里"谁来当裁判"那一节——那页的两层裁判(确定性 assertion + 干净上下文的 LLM 打分)正是为了避免"自己给自己判卷",而这里的客服案例说明**连裁判标准本身也可能是错的**。

## 1.5 Graph 拆开就四样

**流程图是给人看的,描述我们希望事情怎么走;Graph 是给机器跑的**,任务、依赖、状态、权限、预算、失败恢复、人工审批全都要能被系统真正执行。 [文章]

```
G = ( V 节点, E 边, S 状态, P 策略 )
```

| 部分 | 是什么 |
|---|---|
| **V 节点** | 干活的单元,一进一出、只干一件事。可以是专门化智能体(研究员/写手/审稿人),也可以是确定性步骤(一次函数调用) |
| **E 边** | 节点间的路由,回答"接下来去哪"。直通/条件分支/扇出/扇入/回环(审稿不过退回重写) |
| **S 状态** | 沿边流动、大家共读共写的对象,记录任务、证据、预算、产物、检查点。**它把一堆各干各的智能体捏合成一个系统** |
| **P 策略** | 约束谁能创建节点、调用工具、修改图、产生副作用。谁能查库、谁能发邮件、谁必须等人批 |

最贴切的比喻是**公司的组织架构图**:一家公司不会让同一个人又做研究、又写方案、又当评审。"**智能体从一个 while 循环,毕业成了一张组织架构图。**" [文章]

两个要澄清的混淆 [文章]:
- **不是知识图谱**。知识图谱组织"系统知道什么",这里的图组织"系统由谁组成、工作如何流动"。
- **不等于把现有流程画成流程图**。只有当节点能独立执行、边携带明确状态、过程能被检查暂停恢复追踪时,这张图才算系统结构,而不是展示材料。

## 1.6 三种编排形状 + Anthropic 五种模式

### 1.6.1 三种拓扑 [文章]

- **菱形(扇出扇入)** —— 最高频。多个智能体并行取信源(Fan-out),程序去重分类后交给拟稿人(Fan-in)。市场调研、代码评审、研究报告换个信源就能复用。
- **主管模式(Orchestrator-Workers)** —— 主管居中调度,分派给专职工人,自己负责规划和汇总。**Anthropic 的 Research 系统用的就是这个**。
- **流水线(Pipeline / Prompt Chaining)** —— 拆成一串固定步骤,中间加程序化检查点(gate)。用延迟换准确率。

**这三种不是互斥的框架选型,而是可拼装、嵌套的积木。** 真实生产系统常常是主管模式套着几个菱形,菱形里又是流水线。

### 1.6.2 Anthropic《Building Effective Agents》的五种模式 [信源✓]

| 模式 | 做什么 | 什么时候用 |
|---|---|---|
| **Prompt Chaining** | 拆成一串步骤,每步处理上一步输出 | 能干净拆成固定子任务,用延迟换准确率 |
| **Routing** | 先分类再导向专门处理,关注点分离 | 输入种类多,一套提示优化一种会拖累另一种 |
| **Parallelization** | 切成独立分支同跑再汇总(即菱形) | 子任务能独立,或需多视角交叉验证 |
| **Orchestrator-Workers** | 主智能体动态拆解、分派、汇总 | 子任务**无法预先确定**,需运行时决定 |
| **Evaluator-Optimizer** | 一个生成、一个评估打分,迭代到达标 | 有明确评价标准,且迭代能带来明显提升 |

> **Anthropic 对框架的中肯提醒**(值得单独记)[信源✓]
> LangGraph、Bedrock、Rivet 能简化底层活让你快速起步,但它们**加了一层抽象把底下的提示和响应盖住了,反而更难调试**,也容易诱使你在简单方案就够用时把系统搞复杂。
> 建议**先直接用 LLM API**,很多模式几行代码就能实现;要用框架也务必搞懂它底下的代码。

## 1.7 核心:确定性,不是智能体数量

全文最重要的一章。翻车的根子是:**模型既当运动员,又当裁判。** 让写代码的智能体在写它的上下文里审自己的代码,它几乎永远说没问题。 [文章]

### 1.7.1 Verifier(验证器)

把"做判断"和"做验证"拆成两个独立节点。验证器的职责**不是再写一份答案,而是专门试图推翻前一个结论**,扛得住才放行。关键是它要用**一双全新的、干净的眼睛,只看最终结果,不看是怎么憋出来的**。 [文章]

三种验证打法 [文章]:
- **对抗式** —— 派多个怀疑者分头驳同一个结论,多数没驳倒才算站得住
- **多视角** —— 正确性、安全性、能否复现,各查各的
- **评委制** —— 多方案并行打分,选优胜者再吸收亚军的好东西

配一个 **Router** 像医院分诊台,按重要程度导向不同检查强度:普通观点快速核对,重要数据和安全结论多角度交叉审。

### 1.7.2 最硬的确定性来自代码和现实

确定性的活(格式校验、跑测试、去重、排序、算预算)**就该交给普通代码**——让模型判断 JSON 合不合法既不稳定又费钱。
一句话:**让模型的判断力落在节点上,让代码的可靠性落在边上。** [文章]

> **全网关于 Graph 最重的一句警告** [文章]
> 如果一张图里所有节点都在互相引用模型生成的结论,**没有一个节点真的去碰一下现实**,那它只是一台更精致的自嗨机器——有人称之为"**一个项目管理做得更好的、更大的幻觉**"。
> 真正的锚点必须是无法狡辩的硬事实:测试真的跑过、钱真的到账、用户真的留下、库存真的对上、线上指标真的恢复。

> [AI 补充] 这段和 [[AI Agent 的可验证开发体系]] 是**同一个论点的两次独立表述**,而且都指向"确定性断言"。那页作者来自芯片验证行业(assertion/coverage/scoreboard),这篇来自 Agent 平台工程,两条完全不同的经验路径得出同一结论——这种独立收敛比任何单篇论证都更有说服力。

## 1.8 完整例子:同一任务,Loop vs Graph

任务:**做一份每日研究简报**——读几个信源、写成一页摘要、发邮箱前先核对准确性。 [文章]

### 做法一:一个臃肿的 Loop
一个智能体搜信源、把原始结果一股脑塞进上下文、起草、然后审查自己的草稿。
问题:等它开始审查时上下文已是一锅粥,**它是在写出这份草稿的同一个上下文里审查它,等于让作者给自己判卷**。而且循环天生顺序,只能一个信源一个信源读。

### 做法二:三节点小图
- **研究员节点** 扇出到多个信源并行搜集,**只返回结构化笔记,绝不写成文**
- **写作节点** 只拿到干净笔记,看不到杂乱原始网页
- **审稿节点** 在全新上下文里只看简报和验收标准,不合格打回

### 但小图不是白来的 [文章]
代价是:维护三个提示词而不是一个、要设计节点间状态结构(研究员到底交给写作什么)、要应对一批新失败模式(合并时漏信源、路由 bug 死循环、状态从一个节点泄漏到下一个)。

> **这个例子最关键的一句**
> 对于一份**每天都要跑**的简报,这些额外开销换来实打实的质量提升,值。
> 但对于一个**只跑一次**的任务,它就是**纯粹的税**。
> **这笔账,就是要不要从 Loop 升级到 Graph 的全部决策。**

| 维度 | 臃肿 Loop | 三节点小图 |
|---|---|---|
| 上下文 | 全糊在一起,越滚越脏 | 每节点各自干净、隔离 |
| 审查 | 作者审自己,几乎必过 | 全新上下文,真正挑错 |
| 搜集 | 顺序读,慢 | 并行扇出,快 |
| 可读性 | 一长段对话记录,靠反推 | 一张能读懂的图 |
| 成本 | 一个提示词,起步低 | 三个提示词+状态结构,起步高 |
| 适合 | **只跑一次**的任务 | **每天都跑**、要质量的任务 |

## 1.9 什么时候该用,什么时候不该(最实用的一节)

**别为了 Graph 而 Graph。** Anthropic 见过太多团队花几个月搭复杂多智能体架构,最后发现**改进单个智能体的提示就能达到同样效果**。 [信源✓]

### 1.9.1 三个成本数字(我逐条核实过 [信源✓])

| 数据 | 含义 |
|---|---|
| **90.2%** | 多智能体研究系统(Opus 4 主 + Sonnet 4 子)在内部 research eval 上超过单智能体 Opus 4 的幅度 |
| **15×** | 多智能体系统的 token 消耗约为普通对话的 15 倍(单智能体约 4×) |
| **80%** | 仅 token 用量一项就解释了 BrowseComp 上八成的性能方差 |

核实结果:三个数字**与 Anthropic 原文完全一致**。补两个原文里有、文章没提的细节 [信源✓]:
- 三因素合起来解释 **95%** 方差(token 用量 + 工具调用次数 + 模型选择)。
- **升级到 Sonnet 4 的收益 > 把 Sonnet 3.7 的 token 预算翻倍** —— 也就是说,**换更好的模型往往比堆架构划算**。这条对"要不要上图"的决策很关键,文章漏了。

### 1.9.2 该用的三把尺子 [信源✓]

- **上下文保护** —— 某子任务产生大量(>1000 token)但对主任务无关的信息,用独立子智能体隔离出去
- **可并行** —— 任务能切成多个独立分支同跑,尤其适合广度优先的研究搜索
- **专业化** —— 不同步骤需要不同工具、提示或专注度,拆开能提升工具选择准确率

反过来,**如果任务就一个目标、一个领域、一个明确的停止条件,清晰的单个 Loop 就是最优解**。比如每天检查一次仓库 CI、失败就总结日志发你——硬拆成十个智能体只会徒增延迟、成本和调试难度。 [文章]

> [AI 补充] Anthropic 原文还有一条限制文章没引:**大多数编码任务真正可并行的部分比研究少得多**,而且 LLM 目前不擅长实时协调和委派。所以"研究类任务适合上图"不能直接推广到"写代码也适合"。

### 1.9.3 治理红线:工作图快变,角色图慢变 [文章]

图允许"任务怎么拆、怎么合"现场灵活调整,这叫**工作图**,可以快变。
**但"谁有权改数据库、谁能绕过审批"这类长期权限,绝不能让模型现场发挥**,这叫**角色图**,必须慢变、可审计。
否则搭出来的不是智能系统,而是一场随时会爆的生产事故。

## 1.10 框架对比与生产案例

Graph Engineering 不是纸上概念。LangGraph、Google ADK、AutoGen 在这个词出现前两年就在用节点/边/共享状态了——**你要是用过它们中任何一个,其实已经在做图工程,只是没这个叫法**。 [文章]

| 框架 | 编排模型 | 状态管理 | 同任务 token | 适合 |
|---|---|---|---|---|
| **LangGraph** | 有向图+条件边 | 内置检查点+时间旅行 | ~2000 | 长时运行、需审计回滚的生产管线 |
| **CrewAI** | 角色化 crews | 任务输出序列传递 | ~3500 | 规范化角色协作 |
| **AutoGen** | 对话式 GroupChat | 对话历史为主 | ~8000 | 多模型对话协调的探索性任务 |
| **Google ADK** | 结构化图架构 | 分层协调+A2A | — | code-first、企业级 |

**为什么同一任务 LangGraph 吃 2000、AutoGen 要 8000**:图把智能体之间的"对话"变成了"状态转换",省掉了互相转述背景的那一大堆废话。 [文章]

> [AI 补充] 这组 token 数字来自 DataCamp 2026 的第三方对比,**我没有核实**,而且这类跨框架 benchmark 对任务和实现方式极敏感,当量级参考(相差 4 倍)可以,当精确值引用要谨慎。

### 1.10.1 LangGraph 的持久化执行(单个 Loop 永远给不了的能力)[文章]

编译图时挂 checkpointer,它在每个"超级步(super-step)"结束时存一份全图状态快照,带来四个能力:
- **人在回路** —— 图可在任意节点暂停,等人检查/修改/批准后从断点恢复
- **记忆** —— 多轮交互间保留上下文
- **时间旅行调试** —— 回到任意历史检查点重放,甚至分叉出新路径
- **容错** —— 某节点失败从**最后一个成功的步骤**重启,而不是从头再来

还有个 **pending writes(待写入)** 设计:同一超级步里某节点失败,其他已成功节点的输出会被留存,恢复时不用重跑。

### 1.10.2 生产案例 [文章]

- **LinkedIn SQL Bot** —— 几千名不懂代码的员工用大白话查数仓。路由智能体判断问哪块数据 → 领域专家 → 写 SQL → 自纠错智能体发现错自己修,条件边支持重试 N 次,实在不行升级给人。**查询准确满意度 95%**。
- **Uber 代码迁移** —— 5000 名工程师、上亿行代码。子图给不同语言/仓库各起专门子智能体,上面主管图协调。**检查点机制让系统能扛住 CI 抽风、代码冻结、维护窗口这些必然中断**。节省 **21000+ 工程小时**。

## 1.11 和老工作流、ReAct 的关系:形似神不似

资深工程师最爱争的问题——"这不就是回到 ReAct 之前的老工作流吗?" [文章]

| | 路径 | 节点 | 问题 |
|---|---|---|---|
| **老工作流** | 死的 | 写死的代码 | 遇到没预料的情况完全不会拐弯 |
| **ReAct** | 泡在模型对话里 | 模型全程边想边做 | 事后问"它为什么这么干"只能去杂乱对话记录里考古,难复现难审计 |
| **Graph** | **边固定** | **节点内部自主** | 两层分别解决"稳"和"活" |

**Graph 的巧妙是把"稳"和"活"拆到两层,而不是二选一。** 边和整体结构固定 → 可治理可审计;节点内部保留自主 → 够灵活。

恰好呼应 Anthropic 的官方定义:workflow 是"通过预定义代码路径编排的系统",agent 是"由 LLM 动态决定自己流程的系统",而 **Graph 是两者的融合:用预定义的边框住动态的节点**。 [信源✓]

所以它回到的只是老工作流的"形",内核完全不同——**老工作流的节点是死代码,Graph 的节点里住着能自主推理的智能体**。这不是原地打转,是螺旋上升。 [文章]

## 1.12 作者的结论(以及三句能直接用的话)

**它是一次命名事件,加一次视角上移。** [文章]

- **命名事件那部分是虚的** —— 节点、边、状态、有向图调度、状态机、多智能体编排,计算机科学玩了几十年。**这个词大概率会像 Loop Engineering 一样,几个月后被下一个词盖掉。**
- **视角上移那部分是实的** —— 三件事凑齐了:模型强到能可靠当一个自主节点、框架成熟到能把它们稳稳连起来、社区大到攒出了共同词汇。

作者收尾那句挺有意思:"我们折腾了半天 AI,最后绕不开的居然是最古老的那门学问,**怎么管理一个组织**。怎么分工、怎么定权责、怎么让干活的和监督的分开、怎么在有人掉链子时不至于全盘崩掉。这些问题人类的公司琢磨了几百年,现在只是换了一批员工,重新问了一遍。" [文章]

> **三句能直接用的话** [文章]
> 1. **别为了图而图**。一个清晰的循环能搞定的就别整复杂,先画一张能在餐巾纸上说清的小图。
> 2. **图的价值来自确定性,不是智能体数量**。让模型去判断,让代码去兜底,再配一双独立的、专门挑刺的眼睛。
> 3. **图必须接地气,得有现实锚点**。测试真跑过、钱真到账、用户真留下,不然搭得再精密也就是一台更有组织的幻觉工厂。
