# 1. AI Native 时代的研发组织

> **来源**:这是对一篇观点文章的详细蒸馏,非我个人原创判断。

## 1.1 一句话主旨

AI 不是过去意义上的"工具"(工具延伸人的能力),而是**新的协作主体**。过去两千年所有组织设计,本质都是围绕"人的约束"(管理跨度、沟通带宽、记忆、注意力)建的;当协作主体换成 AI,这些前提开始失效。于是**新瓶颈从"人不够聪明/AI 能力不够"变成"系统的信息形态不是为 AI 设计的"**。

一组开篇数据(内部访谈,深度用 AI 的工程师) [文章观点]:
- 写代码占比 30% → 5%
- 和 Agent 对话占比 5% → 60%
- 纯编码效率提升 10 倍,但**端到端需求交付效率只提升 2~3 倍**(→ 暗示瓶颈不在编码)
- 迭代节奏:上午上线新功能 → 中午 A/B → 下午下线 → 傍晚上线更好版本,**同一天**完成过去 6 周的迭代

## 1.2 论证脉络(为什么会得出这些结论)

作者的推理是一条链,不是散点。按顺序:

### 1.2.1 组织的本质是"信息路由",核心约束是人

- 组织演化两千年,本质都在解决同一件事:**信息怎么路由**。 [文章观点]
  - 罗马军团 8→80→480→5000 嵌套 = 把信息路由协议化。
  - 1806 普鲁士总参谋部 = 中层管理雏形(专门做信息整合和决策预演)。
  - 1840s 美国铁路第一张组织架构图 = 为了避免火车相撞。
- 唯一不变的核心约束:**管理跨度 3~8 人**——一个人能直接管的下属数量。这不是文化,是人这个生物的硬限制。所有组织形状都是在这个限制上做的妥协。 [文章观点]

### 1.2.2 所有组织设计都是"人的镜像"

- 康威定律(组织结构=系统结构):因为团队内沟通成本 << 跨团队,模块边界必然与团队边界重合。 [信源:Conway 1968]
- 人月神话(加人无法加速延期项目):因为沟通成本随人数指数增长。 [信源:Brooks 1975]
- Taylor 科学管理拆分岗位:因为人的注意力稀缺。
- manager 评价制 + 强制分布:因为员工产出不可观测,让"信息上最近的人"代理评估。
- → 这些定律/制度不是抽象工程哲学,是**人的协作物理学**的具体实现。

### 1.2.3 AI 是"人的镜像反面",前提失效

AI 的特点正好和人相反:

| 维度 | 人 | AI |
|------|-----|-----|
| 沟通 | 有衰减 | 无衰减 |
| 激励 | 需要 | 不需要 |
| 疲劳/情绪 | 有 | 无 |
| context switching | 成本高 | 极小 |
| 记忆/注意力 | 有限 | 几乎无限 |

→ 上一节所有"以人形约束为前提的设计",前提开始失效。 [文章观点]

### 1.2.4 双层结构:Harness + Hive Mind

观察真正在做 AI Native 的团队(Anthropic、CREAO、内部先锋组),共同形态是**两层,运作逻辑相反**: [文章观点]

- **底层 Harness 层**:代码、测试、流水线、文档、世界模型。所有信息做成 AI 友好形态。**越结构化越好,AI 主导**。
- **上层 Hive Mind 层**:对话、试错、idea 涌现、Yes-and。**越松散越好,人主导**。

关键洞察:Anthropic 几乎肯定有最精密的 Harness(Claude 就是它造的),却在其上运行混乱文化——**两者不是替代,是叠加。结构化是为了释放无结构协作,不是用结构控制一切**。

### 1.2.5 范式转换:从 Org Chart 到 Execution Graph

- "Once AI becomes agentic, the organization stops being accurately described by an org chart. It becomes an execution graph." [信源:Ken Huang]
- Execution Graph = 把人、agents、数据、权限、工具、审批当作**同等节点**的活网络。节点间不是"汇报关系",是"意图到行动的转化链路"。
- **核心问题变了**:
  - 旧问题:ownership——"谁拥有这件事?"
  - 新问题:routing + governance——"意图从哪里进入系统?怎么翻译成行动?什么约束让这个行动安全?"
- **被低估的红利**:组织最小单元从"人+长期关系网"(粘性极高,reorg 要 6~12 个月)变成"任务+上下文+权限+工具"(大部分是机器可读 artifact)。→ **重组成本从季度级压到 week 级**,这是数量级跃迁。适应性速度本身的升级。

### 1.2.6 人既是瓶颈,也是兜底(全文最关键的翻转)

- 过去几十年抱怨的组织效率问题(会议多、对齐成本高、信息失真、流程慢),矛头都指向人 = **人是瓶颈**。
- 但很少有人正面说的另一面:一份不完整的需求、没注释的代码、不一致的 API、口头潜规则……系统还能运转,是因为**人在用灵活性/推理/社会沟通悄悄补缺口**(开会问、走过去问老王、凭经验猜、跑预发试)。这些是**人扛在肩上的隐性成本 = 人是兜底**。
- 系统长期容忍大量不规范/不结构化/不完整信息,只要人够聪明勤奋熟悉,缺陷就不上升为瓶颈。
- **AI 接管执行后这一面翻转**:AI 没有"猜"和"问老王"的能力,它要的是结构化、可查询、可执行、确定性的信息。而传统系统从来不是为 AI 设计的。
- → **新瓶颈的真相:不是 AI 能力不够,是系统的信息形态不够**。过去被人吸收的"信息隐性化/非结构化/缺失"成本,第一次以瓶颈形式暴露。

### 1.2.7 新瓶颈 = 信息形态的人形偏置

- 内部大规模 AI 化调研(对象是已在深度用 AI 的员工):提及最多的期待**不是模型更强、响应更快,而是"系统打通与数据整合"**——所有岗位/层级提及频次最高,断崖式领先第二名。 [文章观点]
- 痛点:AI 无法触及日常工作的数据和系统(钉钉、数据系统、研发系统、邮件、审批流)。
- 结果是反讽的人机协作:**员工在做"人肉中间件"**——手动导出数据、复制粘贴进 AI、再把输出搬回业务系统。AI 已经能处理,但系统没给 AI 留接口。**这是当前 AI 化最大的隐性税**。
- **Harness Engineering** [信源:OpenAI, 2026 初]:工程团队首要职责不再是写代码,而是让 Agent 能干活。Agent 出错时不问"它怎么这么笨",而问"我们少了什么能力?怎么让它对 Agent 来说 legible + enforceable?"
- "AI 友好" 5 维度(内部工程师归纳):测试完备性、环境完备性、架构合理性(无循环依赖/无跨服务隐式调用)、端到端测试可执行性、文档充分性。→ 今天的系统"能用"是因为人聪明,不是因为 AI 友好。
- **复利特性**:Harness 一旦跑起来,AI 接管越多 → 失败信号越丰富 → Harness 优化越快 → 飞轮加速。**早建的公司过临界点后突然加速,晚建的被远远甩开**。

## 1.3 组织重构:管理塌缩与三柱架构

### 1.3.1 管理塌缩(不是消失)

- CREAO CTO Peter Pang:两个月前 60% 时间管人,现在不到 10%。 [信源]
- Block:"永久的中层管理层不再必要"。 [信源]
- 但作者说这结论太粗糙。把管理者工作拆成 **10 件事**,命运分化: [文章观点]

| 类别 | 具体工作 | AI Native 下的命运 |
|------|----------|--------------------|
| 可被系统替代 | 战略传导、信息聚合、资源协调、日常决策 | World Model 承载 alignment,自动化报告替代汇报 |
| 形态在变 | 重大决策、冲突调解 | 重大决策从 manager 拍板下沉到离客户最近的 DRI;冲突调解总量随团队变小而减少 |
| 不可替代(伦理上必须人做) | 激励、辅导、招聘退出、文化建设 | 保留 |
| 新出现 | 意图教练、身份重建、虚无对抗 | 以前不需要、现在需要、目前几乎没人做 |

→ **管理塌缩,不是管理消失。是管理在重新选择它的位置**。

### 1.3.2 Architect:新组织的最高杠杆点

- Architect = **设计"教 AI 怎么工作"的人**。不写代码、不堆功能,而是为整个 Execution Graph 设计架构:定义系统能力边界、设计 SOP、建测试基础设施、搭集成与 triage 系统、定义"什么叫好"。
- 本质:**把组织的隐性 know-how 翻译成 AI 可消化形态的人**。每份 SOP、每个判据、每段架构决策都直接进 Harness 层、直接决定 AI 接管深度。
- 特殊性:**要求最懂这个领域的人来做**(写好测试需懂业务、写好 SOP 需做过这事、定好判据需有品味、设计好架构需见过失败模式——都是资深工程师特质)。
- → 一个 Architect 的产出被 N 个 agent 复用、被多个 domain team 依赖、被多个项目继承。**能找到/留住/让资深工程师主动转身做这个角色,是新组织最稀缺的资本**。

### 1.3.3 Agent 作为"新员工阶层"

- "Agentic AI introduces a new employee class." [信源:Ken Huang]
- Agents 需要 onboarding、scoping、supervision、offboarding。但和人有 **4 个最危险的不对称**:
  1. 可被无限复制
  2. 同小时既 brilliant 又 brittle
  3. compliance-blind by default(默认无视合规)
  4. fast enough to fail at scale(快到能规模化地犯错)
- → 管 agent 不是管软件、也不是管人,**需要第三套治理框架**。

### 1.3.4 Platform 三柱架构

Ken Huang 给的最具体回答: [信源]

- **柱 1 · Agent Platform Group**——中央团队。runtime 标准、权限、日志、可观测、评估 harness、安全部署。"This is not 'AI research' in the romantic sense; it's production engineering plus governance." = Architect 角色的组织化形态。
- **柱 2 · Domain Teams**——业务团队。"Own outcomes rather than models."(对结果负责,不对模型负责)。3-5 人垂直功能小组是其实现。
- **柱 3 · Risk and Oversight**——治理层。"An immune system rather than a bureaucratic brake."(免疫系统,不是官僚刹车)。"When governance is done well, it does not slow the Hive Mind down; it keeps it alive." 这一柱最被低估——别的讨论都在讲创造性/效率/文化,没人正面答"出事了怎么办"。"Assuming nothing will go wrong is not optimism; it's negligence."

**双层 × 三柱叠加**(见原文架构图 `![[../../assets/wx-9f23657150.png]]`):

```
        Harness 层 · 结构化 · AI 友好
        ┌─────────────────────────────┐
        │ 柱1 · Agent Platform Group  │  建造者
        │ runtime/权限/评估/部署       │
        └──────────┬──────────────────┘
   提供能力         │ 协作
Hive Mind 层 ·松散  ▼                  │
┌──────────────────────┐              │
│ 柱2 · Domain Teams   │              │
│ 3-5人小组+数字员工    │              │
│ 对客户结果负责         │              │
│ Own outcomes,not models│            │
└──────────┬───────────┘              │
   遵守约束  └──────────┐   ┌──────────▼──────────┐
                        ▼   │ 柱3·Risk & Oversight│  守护者
                            │ 策略/阈值/事故响应   │
                            └─────────────────────┘
```
横看两层(Harness 结构化底层 / Hive Mind 松散上层),竖看三柱(柱1 建造底层、柱3 守护底层、柱2 在上层探索交付)。

- Huang 给的 **6 项基本功**:枚举 agents、权限纪律、梯度自治、日志、评估 harness、事故响应。都不"性感",但基础设施工作有复利。

## 1.4 关键反转:Death of ego 是有边界的

这是全文最有辨识度的观点,作者主动给前面判断加边界条件。

- 引用素材普遍朝"最大化透明 + 死 ego"推。Steve Yegge 用了 "death of the ego"。 [信源:Yegge]
- 但作者认为**一刀切会扼杀创新**。关键是区分两种 ego:
  - **防御性 ego**(护地盘、藏失败、邀功避责)= 旧组织协调机制的副产品。**Yegge 想杀的是这种,对的**。
  - **生产性 ego**("这是我要弄明白的"、"我不接受这个答案"、"没想透睡不着")= **创新的发动机**。被杀掉时没人会立刻看到。
- 为什么生产性 ego 是发动机?困难问题需要数月级持续注意力(靠"我的"作锚点)、创新要求愿在公开显得愚蠢(skin in the game)、死胡同期需要顽固、创新常反共识(Hive Mind 越成熟反共识声音越难维持)、凌晨 2 点的执着(只发生在你真觉得"这是我的事")。
- **这五件事 AI 当前架构上做不到**:AI 没有自我连续性——**transformer 是 stateless 的**,本质上排斥"在一个问题上保持几个月在乎"。→ **创新工作是人在 AI Native 组织里真正不可替代的领域**。
- 三类工作 / 三种治理:

| 工作类型 | 治理方式 | ego 处理 |
|----------|----------|----------|
| 执行类 | 越透明越好 | 杀掉防御性 ego(对) |
| 优化类 | 结构化但留批判空间 | 抑制 ego |
| 创新类 | 保护半成形想法,半私密不强制广播 | 主动维护生产性 ego |

→ 用同一种治理(Death of ego 一刀切)管三类工作 = **执行高效 + 创新死亡**。

## 1.5 三个案例(检验前面的推理)

1. **先锋**(内部 4 位深度用 AI 的工程师):写代码 30%→5%、和 Agent 对话 5%→60%、3-5 人小团队按垂直功能划分(不再有产品/前端/后端边界)、沟通从"需求评审驱动"转向"成果评审驱动"、**决策权与开发权分离**("决策权还在领域专家手上,但开发权可以交出来"——访谈原话)。= AI Native 跑通后的样子。
2. **全员**(数百条系统打通调研):普通员工已大量用 AI,但卡在"人肉中间件"阶段。= AI 化中段的真实状态。
3. **反例**(内部 3 人小组两阶段对照):同批人同能力。阶段1 做有挑战有自主权的项目,自评行业前沿、士气高;阶段2 被调到他人主导项目,贡献关键但汇报只字未提,士气崩塌想退出。**唯一变量是 ego 投入条件**。
   - 尖锐观察:**"可见性 ≠ 被看见"**——代码 commit 都在(可见性),但管理者没在汇报里念名字(没被看见)。新系统很容易把前者当成解决了后者。

## 1.6 转型的真实代价:人怎么办

- 内部自嘲:"把自己**蒸馏(distillation)**完,就在组织里没位置了"。员工每写一份 SOP、每教 AI 一个流程,都是把知识导出到组织资产——**感觉是合作,结构上接近替代**。
- 三个不能回避的原因:
  1. **培养断裂**:旧路径(day1 写简单代码 → 写复杂 → 设计系统 → 定战略)每步连续。新路径 day1 AI 已在写代码,入门级岗位可能消失。每家公司不招 day1 是局部最优,但**整个行业不招 day1,三五年后 senior 池枯竭 = 产业级灾难**。
  2. **蒸馏焦虑破坏转型**:员工意识到"说得越多被替代越快"→ 关键知识藏匿 → 而 Harness 工作恰恰需要员工说出隐性约定 → 员工不说 Harness 就做不成 → 最优秀的人先走(外部选择最多)→ 转型失败。
  3. **行业级负反馈环**:用 AI 替代而非放大人 → 竞争压力让其他公司跟着收缩 → senior 池/Architect 储备变薄 → "death of expertise" 方向互相加速 → 几年后整个行业判断力被同步抽空。
- 避免最坏情况的方向(作者不假装有完美方案):
  - 明确 AI 红利分享方式:**扩展组织边界做以前做不了的事** vs **收缩团队**——两条路给员工信号完全相反。
  - 转型必须有真实"接住"机制(Architect 通道、跨领域 DRI、新业务负责人、真实过渡支持),不能只是 PPT。
  - 诚实分类哪些岗位形态在变(模糊承诺比明确告知更伤人)。
  - **评价系统必须跟着变**(口头说"判断比执行值钱"但 KPI 还是产出量,员工不会信)。
- 收束:AI Native 最难的不是技术,是处理"被转型"的人。**人不是 capability units,是有 ego/焦虑/家庭/身份的存在。AI Native 不是把人当 capability 调度,是给 capability 之外的部分留出位置**。

## 1.7 作者承认"还没解决的"(诚实的开放问题)

1. **AI 信任度**:CR 和缺陷分析等高风险环节,AI 产出仍需打问号,人工审核又跟不上——"不敢全信、人工又扛不住"的两难。
2. **绩效失效**:旧依据(老板目击)失效,新依据(artifact 可见 + recognition 主动)还没建立。
3. **3-5 人小团队是临时最优还是终态**:目前的"魔法"可能来自三个临时条件——探索者效应、过渡期人形需求、审稿层价值。
4. **AI 知识资产继承**:员工花几个月调教好的 agent,人走时怎么办?目前没有任何公司有完整方案。

## 1.8 十条关键判断(作者的收尾)

1. Harness 工作不显眼,但它是组织未来速度的**复利本金**。早晚投入的差距是指数级,不是线性。
2. 别把 AI Native 当"又一次 reorg"——这是错配。它的价值是**让组织未来不再需要痛苦的 reorg**。Harness 复利让组织变快,Execution Graph 复利让组织能持续应对变化。
3. 解决 Architect 的激励问题:把"被威胁的资深工程师"转化为"被赋能的 Architect"——给身份、给权力、给资源。
4. 分辨节点类型:执行节点全透明+死防御性 ego;创新节点保护性环境+维护生产性 ego。搞混 = 执行高效+创新死亡。
5. 开始做 **agent 名册**——你不可能治理你叫不出名字的东西。

最后回到 Block 的问题:**"你的公司理解什么是真正难以理解的?这个理解每天都在变深吗?"**
- 答案是"没有" → AI 只是降本故事(砍人头、提毛利、最终被更聪明对手吞并)。
- 答案足够深 → AI 不是增强你的公司,是**揭示你的公司到底是什么**。

## 1.9 概念速查(唤醒用)

- **协作主体 vs 工具**:AI 是前者不是后者。
- **管理跨度 3~8**:组织形状的生物硬约束。
- **协作物理学**:康威定律/人月神话/评价制都是人形约束的产物。
- **Harness 层 / Hive Mind 层**:结构化 AI 主导 / 松散人主导,叠加非替代。
- **Org Chart → Execution Graph**:节点=任务+上下文+权限+工具;问题从 ownership 变 routing+governance。
- **人肉中间件**:员工手动搬运数据,当前 AI 化最大隐性税。
- **信息形态的人形偏置**:新瓶颈本质。
- **Harness Engineering**(OpenAI):让 Agent 能干活;legible + enforceable。
- **AI 友好 5 维度**:测试/环境/架构/端到端测试/文档完备性。
- **管理塌缩**(非消失):10 件事命运分化。
- **Architect**:教 AI 怎么工作,最高杠杆点。
- **Agent = 新员工阶层**:4 个危险不对称,需第三套治理。
- **Platform 三柱**:Agent Platform Group / Domain Teams / Risk & Oversight。
- **Death of ego 有边界**:杀防御性 ego,护生产性 ego(创新发动机,AI 因 stateless 做不到)。
- **可见性 ≠ 被看见**。
- **蒸馏焦虑**:说得越多被替代越快 → 知识藏匿 → 转型失败。
- **复利**:Harness 复利(变快) + Execution Graph 复利(能应变)。
